## Context

Design § 6.5: the before/after view compares "every signal window before vs after one deploy instant", and "a **deploy instant** is the time a workload actually changed (pod creation, merge time), never an announcement". No `ess/1` document declares a deploy instant, and `AGENTS.md` (order of work) puts ESS first: this story specifies the noun before `story:m4-deploy-instants` records it and `story:m4-before-after` reads it.

- `generated/spec-types`, `generated/thalamus-model` and `spec/suite.json` are regenerated by `story:m0-workspace`, `story:m2-spec-history-records`, `story:m3-vocabulary-mapping`, this story and `story:m5-spec-integration-records`. This story lands after `story:m3-vocabulary-mapping` (`depends_on`, reason: both regenerate these three; `story:m3-vocabulary-mapping` itself lands after `story:m2-spec-history-records`), so of the stories before M5 it is the last that regenerates them; `story:m5-spec-integration-records` lands after it.

## Work

- `spec/domains/deploy.yaml`, domain `thalamus.deploy`:
  - types: `DeployId` (newtype, prefix `dep_`); `DeployOrigin` (enum `pod_created`, `merged`; closed, so an announcement has no variant); `DeployProvenance` (`producer`, `version`, `adapter`, `connection`, `operation`).
  - entity `DeployInstant`: identity `deploy_id`; fields `ts` (the instant the workload changed), `origin`, `workload` (the object or project the change belongs to, as the source names it), `ref` (the revision or merge reference the source gives), `dims` (`Map<thalamus.dimension.DimensionKey, thalamus.dimension.DimensionValue>`, with the same `UNMAPPED:` marker as `spec/domains/observation.yaml:142`), `provenance`; lifecycle `Recorded` only.
  - actor `thalamus.deploy.DeployReader`; command `RecordDeployInstant` with outcomes `recorded` and `already-recorded` (same `deploy_id`; nothing written); event `DeployInstantRecorded`; view `DeployInstants` (`order_by: [ts asc]`).
  - An `UNMAPPED:` marker on `deploy_id`: the id is derived from origin, connection and `ref`, so a second read of the same change is `already-recorded`; held by a Rust test in `story:m4-deploy-instants`.
- `spec/system.yaml`, `spec/ess-inputs.yaml` (the domain), `spec/components.yaml` (`thalamus-service` owns `thalamus.deploy`, accepts `RecordDeployInstant`, publishes `DeployInstantRecorded`).

## Decisions taken here (decomposer call, reversible)

- A deploy instant is a stored record, not a value read from the source each time the view is drawn: the view then works when the source is unreachable and after the source has dropped the object (a replaced pod), and a deploy can be cited by id.
- Two origins only, the two the design names: `pod_created` and `merged`. Another origin is a spec change.
- Deploy instants are kept without a retention limit; they are a few per day.
